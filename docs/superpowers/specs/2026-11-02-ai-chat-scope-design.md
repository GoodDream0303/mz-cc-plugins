## 2. 约束与现状

- 沿用 Python 标准库与 tkinter，不为浮窗引入 Node、Electron、MCP 服务或常驻网络监听器。
- 默认每秒刷新；没有数据变化不重绘。文件发现与增量解析在后台执行，Tk 主线程只接收快照，避免磁盘操作卡住拖动与菜单。
- 浮窗只读 `.claude`、`.codex` 的会话数据；不在轮询中枚举进程、调用 OpenProcess、探测进程存活或终止会话。
- hook 只向本工具自己的运行目录写入最少的状态元数据，不修改原始日志、数据库或 CLI 全局配置。不得保存提示词、工具参数、命令正文、回答或令牌。
- Claude 已有“用户点关闭并确认后”的一次性关闭行为保持原有边界。不得把这一授权扩展为自动关闭任何会话。
- 原工作区含其他任务的未提交修改；本工作使用独立 worktree，提交只包含本工具和相关清单/文档，不推送或合并。
- 本机核查版本为 Codex CLI `0.166.0`。日志已观察到 `task_started`、`task_complete`、`turn_aborted`，当前会话元数据为 `source: cli`、`originator: codex-tui`。
- `thread-writer-locks/<session-id>.lock` 文件本身可能残留。Windows 只读打开后读取第一个字节，在本机活跃会话上返回 `ERROR_LOCK_VIOLATION`（33）；仅凭文件存在不能判定活跃。
- 现有 Claude 插件没有自动化测试；基线 Python 语法及相关 JSON 清单已检查通过。

写入的配置、短期运行状态及诊断日志属于软件运行数据，不作为跨会话用户记忆。不得借本项目创建 MEMORY.md 或类似自动记忆文件。

## 3. 方案比较与选择

| 方案 | 好处 | 代价 |
| --- | --- | --- |
| 完全只读现有数据 | 最接近原有部署方式，无 hook 信任步骤 | 已核查日志不足以保证覆盖等待授权、等待回答的全部状态 |
| 只读为主，插件 hook 补充（用户已选） | 复用现有状态数据，按需补充明确的等待信号 | hook 需要用户在 Codex 中审阅并信任；恢复信号需要验证 |
| 包装或接管 Codex 启动 | 可记录子进程 PID，能控制自己启动的会话 | 改变现有启动习惯，不能自然覆盖已打开会话；本次不采用 |

Claude 继续直接读取自己的会话状态，不为 Claude 新增 hook。Codex 状态适配不依赖 codex-hud 运行，也不加载其 Node 代码；可参考其已验证的事件结构。

## 4. 结构与数据流

逻辑分成采集、归一化快照、界面三个部分。具体模块拆分由实现者决定，以便独立测试，避免为拆分而大改已有窗口代码。

每条会话的公共字段包括：`provider`、`session_id`、`cwd`、`title`、`state`、`state_detail`、`started_at`、`freshness` 和 `capabilities`。主键使用 `(provider, session_id)`，避免两个宿主 ID 撞车。PID 是可选字段，不得用虚构 PID 或将会话 ID 当 PID。

### Claude 采集

保留现有会话文件、标题回退、spare/parked 去重、后台任务和关闭行为。现有红、蓝、绿、黄的优先级保持不变。异常文件沿用上一份有效数据并重试；单个宿主失败不能阻断另一个宿主。

### Codex 发现与活跃性

尊重 `CODEX_HOME`，未设置时使用用户目录下 `.codex`。

1. 列举会话写入锁，跳过协调锁，严格验证会话 ID 格式及路径范围。
2. 使用只读 `CreateFileW`/`ReadFile` 观察已有字节锁，不申请锁、不写文件。只有明确的锁冲突可以作为当前版本的活跃信号；访问拒绝等其他错误不得等同活跃。
3. 维护 rollout 文件路径索引，发现与更新采用独立、低频且有工作预算的扫描；稳定轮询不递归读取整个历史目录，不重读全部旧对话。
4. 只读取候选文件的有限长度头部元数据，确认 ID 和来源。只展示 CLI 主会话，过滤子 agent 与其他宿主。
5. 标题优先采用 `session_index.jsonl` 中的显式会话名（增量读取），其次元数据标题，再回退工作目录名及短 ID；不读取首条用户消息来命名。

首版不依赖 SQLite，以免把 `mode=ro` 误当作绝不会创建 WAL 共享内存等附属文件的保证。若日志版本/写入锁格式不支持，应明确报告 Codex 数据源不可用，不能把历史对话当作活跃窗口展示。

活跃性必须在本工具创建的临时测试文件上验证锁持有/释放两态，并补一次真实 CLI 正常退出验收。不得锁住真实会话文件。会话退出后清除其内存状态；短暂 I/O 故障可保留上一帧并标明数据暂未更新。

### Codex 常规状态

按偏移量增量读取日志，缓存只保留所需状态。兼容当前观察到的生命周期事件，并用真实样本核对事件中嵌套的工具项。

- 根回合开始：绿灯。
- 根回合完成或被中断、会话仍活跃：黄灯。
- 明确的等待授权或等待回答：红灯。
- Codex 子 agent 不单独占据主列表，也不因为出现子 agent 就把主会话改成蓝灯；未取得可靠后台任务语义时，蓝灯继续用于现有 Claude 后台会话。

处理半行写入、UTF-8 跨块、非法行、单行超长、文件替换/截断、会话恢复和旧回合事件。启动时不能为了恢复状态一次性阻塞读完大文件；采用有预算的增量追赶，未追赶完标记为同步中，不宣称最新状态。

## 5. Codex hook 与等待状态

hook 是被动观察者，不批准、不拒绝工具，不添加开发者上下文，不输出对话内容。正常路径输出符合事件协议的空 JSON 并返回成功；畸形输入或本工具 I/O 故障也应尽量成功退出，不阻碍 Codex 工作。诊断只记错误类型，不记原始 stdin。

优先使用必要的少量事件：`PermissionRequest`、`Stop`、`Interrupt`、`SessionEnd`，以及针对用户输入工具的 `PreToolUse`/`PostToolUse`。是否还需其他事件，在兼容性验证后决定，避免为每个普通工具额外启动 Python。

`PreToolUse` matcher 必须来自实际验证过的工具名称，不假定 `request_user_input`、异步提问工具及 code mode 嵌套调用一定具有相同的 hook 行为。异步提问工具的“调用返回”不等于“用户回答”，不能仅靠 PostToolUse 清除它。

hook 只写入 `%LOCALAPPDATA%\ai-chat-scope\runtime\codex\<home-key>\<session-id>\`。`home-key` 根据规范化 Codex 数据根生成，不从不可信输入直接拼路径。允许持久化的字段限于来源、会话 ID、回合/工具调用 ID（若有）、事件类型、工具名称、时间与格式版本。不得保存命令、参数、问题和回答。

采用每个事件一个原子发布的小文件，避免并发 hook 覆盖同一个状态文件；文件名由本工具生成。归并时按会话、回合和调用归属处理，避免延迟到达的旧事件重设当前回合。事件收敛和退出清理由本工具处理，只清理自己的运行目录。

### 实施前的兼容性验证关口

官方文档列出了 `PermissionRequest`，但没有独立的“用户已批准/拒绝”事件；它的公开字段也没有承诺 `tool_use_id`。`PostToolUse` 通常在工具结束后发生，不能直接视为授权已处理。当前检查过的 rollout 主要包含完成事件，尚未证明工具开始信号对所有工具实时落盘。

因此，首个实施任务必须验证以下完整状态序列，形成可复核结论后再定最终状态归并逻辑：

1. 授权框出现，红灯亮起；批准后执行一个持续数秒的命令，验证红灯在命令完成前恢复绿灯。
2. 拒绝授权、取消/中断回合后，旧等待标记能够解除，不污染下一回合。
3. 同步用户提问在等待时变红、回答后恢复；异步提问必须单独验证，无法获取回答完成事件时不能假装已覆盖。
4. 同回合并发工具及旧事件延迟到达，不造成等待状态串线。

测试先使用独立样本/测试入口；需要真实 CLI 对话时再创建明确标注的测试会话，操作对象必须与用户正在工作的会话隔离。不得替用户回答授权或批量终止真实会话。

若现有公开信号无法达到“用户处理后恢复”的要求，应在该关口报告复现证据并与用户确定降级方案；不得用固定超时猜测、不经说明将红灯保留到长工具结束，也不得直接扩大到终端抓取、进程监控或接管 CLI。用户选择了混合方案，并不表示已同意这些降级。

未安装、未信任 hook 或旧会话尚未加载插件时，常规监视仍可用；用简短的源状态提示说明等待状态未启用，不能展示为红灯能力已正常工作。安装/信任步骤由宿主执行，本工具不代改全局配置。

- Claude 现有过滤/去重/标题与关闭路由不回退；Codex 与 Claude ID 相同也分别展示。

- 增量读取半行、截断、替换和大记录，有读取预算，状态更新不阻塞 Tk。
- hook 输入有界、路径受限、并发原子写入、错误不影响 CLI、不保存对话/参数。
- 配置回退与新配置优先；插件清单和入口路径存在；Claude 不会加载 Codex hook；Codex 行没有误导性的关闭入口。

## 11. 验证后的实现调整

日志/hook 没有批准后的即时回执后，用户选择继续验证实时协议；实际 CLI 已验证只读查询的恢复早于长命令结束。因此实现使用日志读取常规与异步待输入、显式配置的已有 CLI 专用服务提供授权和同步等待；不自动启动服务，不把普通 CLI 的授权能力描述为已启用。

本机 remote CLI 的 source 也可能是 vscode，因此只有显式配置的 CLI 专用端点可提供这一来源的主线程；不自动连接 Desktop 服务。服务须先由 CLI 初始化，避免观察者抢占 originator。

异步只监视“待用户消息”：AgentMessage.questions 置为待输入，后续真实 UserMessage/accepted steering 解除这组注意状态，不声称逐题语义答案已完成；普通 task_complete 不清除等待。

真实 CLI 代表场景、实际后端固定响应测试与回归测试共同验证状态契约。混合 Tk fixture、实际入口与重启分别验证；宿主人工安装和同步选择界面的人工点测不以自动后台测试冒充。细节见验证记录与计划的实施裁定。
