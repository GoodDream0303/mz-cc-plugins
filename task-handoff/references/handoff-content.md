# 失败尝试、验证证据与待人工动作

供 task-save、task-resume 和 task-manage 共用。沿用 handoff.md 的九节结构；这些规则适用于 Codex 和 Claude Code。

## §8：仍有参考价值的失败尝试

保存本次真实尝试过、对当前工作仍有参考价值的失败方案。每项记录：**方案 / 适用条件 / 实际现象或证据 / 失败原因 / 当前结论**。原因未查明就写“未查明”，不把猜测写成根因；未经尝试的设想不记为失败。

- 仍适用的失败结论留在 §8，防止新会话重复试错；重试前先核对原失败条件是否改变。
- 结论已被新证据推翻、条件已不适用，或不再影响后续工作时，按“只搬不删”规则将旧记录原文搬入 log.md，注明原因。§8 留下仍有效的结论，不继续把旧方案视为禁用项。
- 本次没有失败尝试时不补造条目，也不据此声称历史上从未失败。

例：

```markdown
- 失败尝试：增加等待时间；条件：同一复现环境；证据：调整后仍复现，见测试日志；原因：未查明；结论：已撤回，当前条件下不能解决问题。
```

## §6：验证范围、状态与证据

每个验证项分别记录 **验证项 / 状态 / 环境与范围 / 命令或用例及通过标准 / 实际结果与证据来源**。状态使用：

| 状态 | 含义 |
|---|---|
| 已通过 | 有明确执行结果，且在所列环境与范围内满足通过标准 |
| 未通过 | 已执行，有证据表明未达到通过标准 |
| 未验证 | 尚未执行，或现有信息不足以确认结果；注明属于哪一种 |

命令、结果、数量、日志位置或执行版本未提供时写“未提供”，不补造。来自历史交接、用户反馈或本次执行的结果，注明各自来源；历史结果未重新执行时标明“历史记录，本次未复核”，已有明确历史证据的无需一律改为“未验证”。

分开记录构建、模拟/mock 测试、实际运行或硬件验证，以及 Debug/Release 等不同配置。代码存在、编译通过或 mock 测试通过，只能支持各自范围的结论。§3 当前状态据此概括“已完成的实现 / 已通过的验证 / 尚缺的验收”；必要验收未通过或未验证时，不据此宣告整个任务已完成。

例：

```markdown
| 验证项 | 状态 | 环境与范围 | 命令/用例与通过标准 | 实际结果与证据来源 |
|---|---|---|---|---|
| 单元测试 | 已通过 | mock，Debug | test-driver；全部通过 | 本次执行，12 项通过 |
| 实际运行 | 未验证 | 真实设备 | HW-07；连续 100 次无超时 | 尚未执行，等待连接设备 |
| 旧测试记录 | 未验证 | 未提供 | 未提供 | 历史仅记“测试通过”，范围及结果来源待核实 |
```

## §7：待人工动作

除可继续执行的下一步外，将确实需要人工完成的操作单独标为“待人工动作”，逐项记录 **动作 / 执行人 / 解除条件或验收标准 / 阻塞范围**。执行人未知写“待确认”，不自动指定为用户；没有待人工动作写“无”。

只有确认需要人工的操作才列入此处，代理能够完成且已获授权的检查继续由代理处理。明确区分“阻塞整个任务”和“仅阻塞某项验证”；仍有独立工作可继续时列出该工作，不因局部等待自动将整个任务改成 ⬜阻塞。

例：

```markdown
- 下一步：复查 Release 配置。
- 待人工动作：连接设备；执行人：用户（本次已明确）；解除条件：设备可访问；阻塞范围：仅 HW-07，配置复查可继续。
```

## 保存与恢复时的使用

- **save**：据会话事实更新 §6、§7、§8 和 §3；本次验证与尝试同时摘要记入新增 log 条目。原内容被替换或搬出时仍须保留原文，执行现有零丢失校验。
- **resume**：读状态层后区分已通过、未通过、未验证及待人工事项；先检查失败尝试的适用条件，再决定下一步。复述中只突出影响本次继续工作的事项，不为每项验证逐一请求确认。
- **旧文档**：仍可只读恢复，不要求先补字段或迁移。按现有文字提取能确定的事实；证据不足时说明未知或待核实，不将缺字段等同于测试失败。用户明确要求保存或维护时再据实补齐。
- **manage**：精简或迁移时保留仍适用的失败结论、未完成验证与待人工动作；失效条目按既有确认和原文搬迁规则处理。
